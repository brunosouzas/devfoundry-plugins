## Unreleased

### Added
- `mule-engineering` 0.5.0, skill `mule-sdk`: connectors, shared Mule plugins and DataWeave libraries as assets with a public contract (ASSET-1, ASSET-2, both `auto`), ported from the `mule-sdk` skill of brunosouzas/agent-skills with the same IDs. `docs/backlog/eip-from-agent-skills.md` keeps the EIP rules of that repository's `mulesoft` skill (Dead Letter Channel, Correlation Identifier, Publish-Subscribe, EIP-1 to EIP-8) as the source for patterns `integration-patterns` does not have yet. With this, every rule of agent-skills' `mulesoft` and `api` plugins is ported, covered by another rule, or moved to the maintainer's private layer.
- The full-API benchmark, case `TAPI` in `tooling/evals/cases/`: a whole System API (`GET /jobs`, `GET /jobs/{jobRef}`) from synthetic requirements over a fictional SOAP backend with a login session, an encoded query and N+1 reads, starting from a synthetic company template that builds and passes its tests. A 15-item rubric (`grading.md`), a script grader for the checkable items (`grade.py`), a blind review brief, and both runners accept the case with `mvn` pre-approved. It replaces the private full-API case used during development.
- CI with no credentials (`.github/workflows/ci.yml`): the plugin manifests, the scripts' unit tests, the display-name check on the examples in the mule-app layout, and every verified example compiled and packaged with MuleSoft's public repositories (`tooling/ci/`). It catches XML that does not parse or breaks a schema and a pom that does not resolve; MUnit needs MuleSoft's EE repository and stays local (`verify-examples.sh`).
- `api-contracts` 0.4.0: API design as rules, not architecture. LAYER-1 to LAYER-4 (`auto`): an API names its API-led layer (an assumed one goes in "Decisions for you") and keeps to its responsibility (a System API hides its backend and carries no channel rule, a Process API reaches backends through System APIs, an Experience API shapes data for one channel); LAYER-5 (`propose`, the same decision as api-first AFI-6): a new, skipped, split or merged layer is one recommendation with its costs, and until it is decided the agent builds what the requirements describe. NFR-1 (`auto`): every limit the code enforces is in the contract with its error; a value the requirements lack is chosen as the pattern says and listed as an assumption, a value the code does not enforce is an open question. 57 public rules: `propose` AFI-6 and LAYER-5, `ask` AFI-5 and CON-5. `api-first` 0.2.2: AFI-6 names LAYER-5 as the same decision. Solution architecture stays in the team's own process.
- `resilience-patterns` 0.2.0: three patterns join the Circuit Breaker, each with a platform-neutral reference (`session-renewal.md`, `bounded-fan-out.md`, `retry.md`) and one Mule 4 realization (`references/mule4/fan-out-with-session.md`). Session renewal: a cached session the dependency rejects is dropped, the flow logs in again and repeats the call once, never in a loop. Bounded fan-out: a bound on N checked before the first call (`422`), bounded concurrency, and a deadline for the whole request checked before each call (`504`). Retry: only transient failures of calls that are safe to repeat, a few attempts inside the budget, a defined error after the last. Every attempt and login checks the request's deadline; a timeout after its retries is `504`, other transient failures `503`, a login timeout `504` (mule-app MERR-3). Verified example `assets/mule4/fan-out-with-session/` (11 MUnit tests, a carrier stub for the renewal test, six mutation checks). The skill's dependency decisions now ask about cached sessions and the number of calls per request. The missing re-login and the unbounded N+1 calls appeared in every full-API run; retries come with them because a fan-out over a backend that blips needs both.
- Decision classes: every rule with an ID has a `Class:` line, `auto` (the agent applies it), `propose` (it recommends it, says what it costs, and applies it when the developer agrees or the task already asks for it) or `ask` (it stops and asks). All 51 public rules at that point are classified: CON-5 and AFI-5 are `ask`, AFI-6 is `propose`, the rest `auto`. A rule's text says what and its class says how, so an override of the class alone changes how the agent acts. New in `api-contracts`: CON-5 (`ask`), a breaking change to a spec consumers use is the developer's decision; replacing a template's placeholder is not one. A pack or the project changes a class by rule ID with `override: {<ID>: {class: ...}}`, with or without new text; floor rules keep theirs (`profiles/SCHEMA.md`, `references/layers.md`). `resolve-profile.py` reads the classes, applies and reports class overrides, rejects an unknown class and lists the rules of class `ask` and `propose`, and reports a public rule whose `Class:` line is unknown or repeated; its tests check that every public rule declares exactly one class. Versions: `engineering-profile` 0.9.0, `api-contracts` 0.3.0, `mule-engineering` 0.4.0.
- `api-first` 0.2.0: step 0, reuse first. Before creating an API, a spec or a resource, look for the project's specs, the Exchange asset the project names and an existing System API that reaches the same backend, and report each one as reused, extended or not used (AFI-4, `auto`). Publishing, creating an Exchange asset or changing another project's API is a question and a follow-up (AFI-5, `ask`). Calling an existing System API or reaching the backend directly, when the requirements do not say, is a recommendation with its costs (AFI-6, `propose`).
- `mule-engineering` 0.3.0, skills `mule-app` and `dataweave`, ported from the `mulesoft` and `dataweave` skills of brunosouzas/agent-skills with their IDs: display names and flow descriptions (FLOW-2, FLOW-4, with `scripts/check-docnames.py` and its tests), global elements defined once (FLOW-3), layout (LAYOUT-1, LAYOUT-2), properties (CFG-1, CFG-3), the global error handler (MERR-1, MERR-2), structured logs (MLOG-1, MLOG-2), the build (BUILD-1, BUILD-2), and DW-1, DW-2, DW-4 to DW-9 and DWTEST-1. New: MERR-3, a backend timeout reaches the caller as 504 and a failed connection as 503 or 502, never 408. MLOG-2 (no payload or personal data in logs) is a floor rule; from 1.0 on, marking a rule floor would be a MAJOR change. The deliberate changes from the source rules are listed at the top of each `rules.md`. Not ported: the naming rules (FLOW-5, FLOW-6, DW-3), which belong to the profile and private packs, and the deploy and platform rules (PLAT-1, PLAT-3 to PLAT-5). Verified example `mule-app/assets/mule4/error-handling/`, with its mutation checks. The `apikit` example now follows these rules too (display names, flow descriptions, no raw error message in a response, global configuration in `common/`).
- `api-contracts` 0.2.1: CON-2 lists `504`. `api-first` 0.1.1: step 4 names `mule-app` and `dataweave`.

In the full-API runs, a backend helper module landed outside the profile's `dwl/{resource}/` without being reported.
- `api-first` 0.2.1: AFI-3 and step 7, the answer has a "Decisions for you" section before the final table, with every question to the developer: the AFI-5 and AFI-6 questions, each requirement left undone because it waits on the developer (an ambiguity, a doubt about which component owns it, a missing value) and each assumption to confirm. - `engineering-profile` 0.6.0: invokes `api-contract` and `munit` for an API endpoint; `legacyCode: keep` does not keep a template's placeholder spec.
