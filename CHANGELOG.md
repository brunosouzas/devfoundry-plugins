# Changelog

## Unreleased

### Added
- Decision classes: every rule with an ID has a `Class:` line, `auto` (the agent applies it), `propose` (it recommends it, says what it costs, and applies it when the developer agrees or the task already asks for it) or `ask` (it stops and asks). All 51 public rules are classified: CON-5 and AFI-5 are `ask`, AFI-6 is `propose`, the rest `auto`. A rule's text says what and its class says how, so an override of the class alone changes how the agent acts. New in `api-contracts`: CON-5 (`ask`), a breaking change to a spec consumers use is the developer's decision; replacing a template's placeholder is not one. A pack or the project changes a class by rule ID with `override: {<ID>: {class: ...}}`, with or without new text; floor rules keep theirs (`profiles/SCHEMA.md`, `references/layers.md`). `resolve-profile.py` reads the classes, applies and reports class overrides, rejects an unknown class and lists the rules of class `ask` and `propose`, and reports a public rule whose `Class:` line is unknown or repeated; its tests check that every public rule declares exactly one class. Versions: `engineering-profile` 0.9.0, `api-contracts` 0.3.0, `mule-engineering` 0.4.0.
- `api-first` 0.2.0: step 0, reuse first. Before creating an API, a spec or a resource, look for the project's specs, the Exchange asset the project names and an existing System API that reaches the same backend, and report each one as reused, extended or not used (AFI-4, `auto`). Publishing, creating an Exchange asset or changing another project's API is a question and a follow-up (AFI-5, `ask`). Calling an existing System API or reaching the backend directly, when the requirements do not say, is a recommendation with its costs (AFI-6, `propose`).
- `mule-engineering` 0.3.0, skills `mule-app` and `dataweave`, ported from the `mulesoft` and `dataweave` skills of brunosouzas/agent-skills with their IDs: display names and flow descriptions (FLOW-2, FLOW-4, with `scripts/check-docnames.py` and its tests), global elements defined once (FLOW-3), layout (LAYOUT-1, LAYOUT-2), properties (CFG-1, CFG-3), the global error handler (MERR-1, MERR-2), structured logs (MLOG-1, MLOG-2), the build (BUILD-1, BUILD-2), and DW-1, DW-2, DW-4 to DW-9 and DWTEST-1. New: MERR-3, a backend timeout reaches the caller as 504 and a failed connection as 503 or 502, never 408. MLOG-2 (no payload or personal data in logs) is a floor rule; from 1.0 on, marking a rule floor would be a MAJOR change. The deliberate changes from the source rules are listed at the top of each `rules.md`. Not ported: the naming rules (FLOW-5, FLOW-6, DW-3), which belong to the profile and private packs, and the deploy and platform rules (PLAT-1, PLAT-3 to PLAT-5). Verified example `mule-app/assets/mule4/error-handling/`, with its mutation checks. The `apikit` example now follows these rules too (display names, flow descriptions, no raw error message in a response, global configuration in `common/`).
- `api-contracts` 0.2.1: CON-2 lists `504`. `api-first` 0.1.1: step 4 names `mule-app` and `dataweave`.
- `engineering-profile` 0.8.0: `project-profile` invokes `mule-app` and `dataweave` for any Mule code.
- `api-first` 0.1.0, skill `api-first-implementation`: requirements inventory (AFI-1), tests traced to requirements (AFI-2), and a final table of every requirement (AFI-3); it calls `project-profile`, `api-contract` and the platform skills, and takes its requirements from the team's own process. `docs/scope.md`: public practices (API-first, API-led) against private processes (spec-driven development, design reviews, approvals).
- Profile layers (`profiles/SCHEMA.md` v1, `apiVersion: devfoundry/v1`): `extends` lists company or personal rules packs (`kind: RulesPack`, in `engineering/packs/<name>/`), and `rules` overrides, disables or adds rules by ID. Public < packs in order < project. Floor rules (`FLOOR-1`, `FLOOR-2`, `APISEC-1`) cannot be disabled or overridden; an attempt is refused and reported. v0 profiles still read. The merge rules ship with the plugin in `project-profile/references/layers.md`. Marking APISEC-1 as floor would be a MAJOR change from 1.0 on; under 0.x it is a minor bump.
- `engineering-profile` 0.7.0: `project-profile` resolves the layers and reports every changed or refused rule; floor rules in `project-profile/rules.md`; `scripts/resolve-profile.py` (validation and the rules in effect, with tests). `api-contracts` 0.2.0 and `mule-engineering` 0.2.0 apply their rules as resolved.
- Synthetic example pack `profiles/examples/packs/acme-mule/`; eval cases T8 (a pack and a project override) and T9 (a pack tries to disable a floor rule).
- `docs/scope.md`: the three layers (public skills, personal and company rules and agents), what is in and out of scope, and the order of the next pieces.
- `api-contracts` 0.1.0, skill `api-contract`: before an endpoint is built, check that the spec the application loads describes it; replace a template's placeholder spec, or write the spec in the project when the published one lacks the operations (CONTRACT-1, CONTRACT-2). RES, CON and APISEC ported from the `api-spec` skill of brunosouzas/agent-skills.
- `mule-engineering` 0.1.0, skills `apikit` and `munit`: the spec the router loads and implementation flows that match it (APIKIT-1 to APIKIT-3), and endpoints tested through the HTTP listener (MUNIT-5), with mocks matched by `doc:name` (MUNIT-6). Verified example `apikit/assets/mule4/local-spec-router/`, with its mutation checks.
